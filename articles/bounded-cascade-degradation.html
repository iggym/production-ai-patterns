Stop Retrying Your Agents

2025-03-18 Reliability 6 min
"Just add retries — that's what we always do."
Each retry inflates context, burns tokens, and lowers success probability.

In February 2025, an agent pipeline at a mid-stage startup started failing silently. Not crashing — failing silently. Each time a tool-calling step errored out, the orchestrator retried it, appending the error message to the conversation context. After three retries on a single step, the context had grown by roughly 40%, pushing the agent's remaining reasoning into a truncated window where it produced plausible-looking but factually empty output. No error was thrown. No alert fired. The system kept running, delivering worse answers with full confidence. The on-call engineer didn't find out until a customer flagged the degradation — two days later.

BEFORE: "Retries make systems more reliable." AFTER: "Retries on LLM agent steps amplify failure." The turn: your most trusted reliability tool is the mechanism destroying your pipeline.

The Real Failure Mode

Standard reliability playbooks assume each retry is independent: same inputs, same expected output, same cost. An LLM agent step violates all three. Each retry carries a larger context. The model's output is non-deterministic, so the same prompt can produce a different failure. And each attempt burns tokens — real money — for a progressively lower probability of success. The retry doesn't recover the step. It starves every step that follows.

The Pattern

Bounded Cascade DegradationA retry and timeout pattern for multi-step LLM agent pipelines that treats context growth as a first-class failure signal, caps retry-induced context expansion at a defined budget, and degrades the pipeline by skipping or stubbing failed steps rather than re-attempting them with expanded context.

What Fights Back

Four forces push against this. Latency budgets demand fast resolution, making "just retry it" the path of least resistance. Cost governance wants you to stop spending but has no mechanism to see the spending that retry context-inflation causes. The context window is a fixed ceiling — once burned on retries, it's gone. And the expectation of correctness makes engineers unwilling to skip a step, even when retrying it is demonstrably making the overall pipeline worse.

Bounded Cascade Degradation

Three concrete rules. First, define a retry context budget — a hard cap on how many tokens a single step's retry attempts may add to the conversation. Exhausted means degraded, not retried again. Second, implement step stubbing — a degraded step returns a structured placeholder that downstream steps can reason about without the cost of a full re-attempt. Third, set a cascade ceiling — if more than N steps degrade, halt the pipeline and return a partial result with a degradation manifest.

Portkey's AI Gateway implements a version of this at the single-call level: their gateway tracks per-request token consumption and routes to a fallback provider rather than retrying the same provider with an inflated prompt. The fallback preserves the original context size. Vercel's AI SDK takes a complementary angle: when a streaming response fails partway through, their retry logic preserves the partial response as context for the retry attempt, preventing the silent state loss that standard HTTP retries would cause.

What You Trade Away

Bounded Cascade Degradation means accepting partial results. Your pipeline will sometimes return answers with visible gaps instead of confident wrong answers. That's the point. But it also means building downstream logic that can handle those placeholders — engineering work you wouldn't need if retries just worked. And it means defining your retry context budget and cascade ceiling up front, which requires understanding your pipeline's context economics in a way most teams haven't instrumented yet.

The same context-inflation dynamic that destroys agent pipelines on retry is the reason prompt-chaining architectures outperform monolithic agents on long tasks — not because chaining is fundamentally smarter, but because it resets the context bomb at each boundary.

The Evidence

Portkey's published gateway architecture documents their rate-limit-aware retry logic: rather than standard exponential backoff, the gateway reads the Retry-After header from 429 responses and aligns its retry window to the provider's reset clock. Without this, a 30-second backoff against a 10-second rate-limit window wastes the entire reset period — each wasted attempt carrying the full prompt cost. The LangChain community documented the context-growth failure mode across multiple GitHub issues in early 2025, showing that a three-retry loop on a failed tool call could consume 30–40% of a 128k context window in error-recovery text alone. This is roughly the same class of failure that killed early microservice retry storms around 2015 — except those at least returned HTTP 500s. Vercel's AI SDK team described their streaming retry approach as a response to the partial-response problem — dropping a failed stream and retrying from scratch loses intermediate reasoning that downstream agent steps depend on.

But What If...

The strongest counterargument: what if the failure is transient — a momentary rate limit or network blip — and a single clean retry would have fixed it? Bounded Cascade Degradation might skip a step that would have succeeded on attempt two. The answer: the pattern doesn't prohibit retries. It budgets them. A transient failure consumes one retry's worth of context budget and succeeds. A systematic failure — the far more common case in LLM pipelines, where the failure is caused by prompt content, not infrastructure — hits the budget and degrades gracefully instead of silently corrupting the pipeline.

BEFORE: "A partial result is worse than a wrong result — at least the wrong result looks complete." AFTER: "A partial result with a degradation manifest is the only result type that tells the truth about what happened." The turn: the "complete" output you've been serving was never complete — it was just missing its failure annotations.

The Checklist

  • Does your agent orchestrator track context growth per retry attempt, or only per step?
  • When a step fails after exhausting retries, does it return a structured degradation signal or a raw error string?
  • Can downstream steps reason about a degraded predecessor, or do they assume all prior steps succeeded?
  • Does your retry logic account for provider rate-limit reset windows, or does it use generic exponential backoff?
  • If three consecutive steps in a ten-step pipeline degrade, does your system halt or keep producing?

Forces
Latency pressure to resolve fast. Cost governance blind to retry-inflation cost. Fixed context ceiling. Correctness expectation that resists partial results.
Solution
Cap context growth per step (retry context budget). Replace failed steps with structured stubs (step stubbing). Halt pipeline when degradation exceeds a threshold (cascade ceiling).
Consequences
Partial results replace silent corruption. Requires downstream stub-handling logic. Forces upfront context economics instrumentation. Trade: visible gaps for honest output.

An agent step fails on a tool call. You retry three times, each time appending the error to context. What happens to the remaining steps?
Each retry inflates the context, leaving less room for subsequent steps. After three retries, 30–40% of a 128k window may be consumed by error-recovery text alone, causing later steps to produce truncated or empty reasoning — with no error thrown.
Your circuit breaker uses a 30-second cooldown, but the LLM provider's rate limit resets in 10 seconds. What goes wrong?
The breaker stays open for 20 seconds after the rate limit has already reset, wasting the entire recovery window. Each retry attempt during the open state still carries the full prompt cost. The fix: read the provider's Retry-After header and align the breaker's cooldown to the provider's clock.
A streaming LLM response fails at 60% completion. You retry from the original prompt. Why might downstream agent steps now fail?
The partial response contained intermediate reasoning that downstream steps depend on. Dropping it and retrying from scratch creates a hidden state mismatch: the pipeline "knows" about intermediate results that the model hasn't actually produced. The fix: preserve partial tokens as context for the retry, as Vercel's AI SDK does.
