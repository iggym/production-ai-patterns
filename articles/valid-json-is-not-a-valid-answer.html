PATTERN-0601 · RELIABILITY

Valid JSON Is Not a Valid Answer

Structured outputs solved the parsing problem and quietly hid the correctness problem — a schema guarantees shape, never truth.

August 18, 20268 min readResearch window: 2026-07-07 → 2026-08-18

Three things you didn't know you needed

  1. Constrained decoding moves errors; it doesn't remove them. When a model can no longer break the syntax, the errors that used to break parsing come out as plausible values instead.
  2. Your repair loop needs a budget, not a retry count. Re-prompting a model with its own wrong answer adds tokens and anchors it to the mistake. Two attempts are usually the most worth paying for.
  3. The most useful validator is cheap and boring. Cross-field invariants (totals add up, dates are ordered, IDs exist) catch more production defects than an LLM-as-judge, and they cost microseconds.

The Format Drifted, the Code Didn't

In July 2023, researchers at Stanford and UC Berkeley published a simple, uncomfortable measurement. They sent the same code-generation prompts to the March and June 2023 snapshots of GPT-4 and counted how many responses could be executed directly. In March, 52% could. In June, 10% could.[1]

The code itself hadn't got much worse. The model had started wrapping its answers in markdown fences and adding prose around them. Any pipeline that took the response as-is and ran it would have broken overnight, without a deploy, a config change or an alert.

The industry's fix was structured outputs: constrain decoding so the model can only produce tokens that fit a JSON Schema. On OpenAI's own complex-schema evaluation, schema adherence went from under 40% to 100%.[2] The parse errors went away. Many teams took that to mean the problem was solved.

It wasn't. The parse error was the visible failure mode. Once it was gone, the remaining failures became invisible.

Shape Is a Contract, Truth Is a Different Contract

A JSON Schema tells you that refund_amount is a number. It cannot tell you that the number is no larger than the order total. Nor can it tell you that the customer_id exists, that start_date comes before end_date, or that the category the model picked is consistent with the text it read.

Before structured outputs, a confused model often produced malformed output, and your parser complained loudly. Now a confused model produces a well-formed wrong answer, and your parser accepts it. Constraining the shape removed a signal you were getting for free.

Orthodox view

  • "We use structured outputs, so output is validated."
  • Retries happen on parse failure.
  • Success metric: % of responses that parse.
  • Failure surfaces as an exception.

Production reality

  • Schema validity is gate one of two.
  • Repairs happen on semantic failure, with a budget.
  • Success metric: % of responses that are used without correction.
  • Failure surfaces as an explicit degraded result.

Treat model output the way you treat a request from an untrusted client. Parsing it is only the first check, and nobody calls a parsed request authorized.

PATTERN-0601 · RELIABILITY

Two-Gate Output Contract

Intent
Separate can we read it from can we trust it, and give each question its own gate, failure path and metric.
Context
LLM output is used by code: API calls, database writes, routing decisions, UI rendering. Any time a wrong value causes harm that a human won't catch.
Problem
Schema enforcement guarantees well-formed output, but the downstream system needs output that is correct. Without a second gate, semantically invalid values flow through at full confidence.
Forces
  • Latency vs. correctness: every validation and repair round trip adds time to the critical path.
  • Strictness vs. capability: tight format constraints can degrade reasoning quality.[3]
  • Repair vs. anchoring: feeding errors back helps, but the model tends to defend its first answer.
  • Coverage vs. cost: deterministic checks are cheap but narrow; model-based judges are broad but slow and non-deterministic.
Solution
  1. Gate 1 (shape): constrained decoding or strict schema parsing. Fail → one immediate retry, then fallback.
  2. Gate 2 (meaning): a validator chain ordered by cost: type refinements → cross-field invariants → referential checks against your own data → optional model-based judge for the remaining fuzzy cases.
  3. Bounded repair: on gate 2 failure, re-prompt with the specific violated rule (not the whole error dump), and give the repairs a fixed budget (attempts and tokens).
  4. Explicit degradation: when the budget runs out, return a typed Degraded result (ask a human, use a rules-based default, or refuse). Never return the last invalid attempt.
  5. Record which rule fired: each violation increments a counter tagged by rule, model and prompt version.
Consequences
Benefits: wrong answers turn into countable, routable events; violation rates per rule become a regression signal for prompt and model changes. Liabilities: adds p95 latency on the repair path; invariants have to be maintained alongside the schema; overly strict rules can cause degradation storms.
Related patterns
Bounded Cascade Degradation · Prompt Flight Rules · Decision-Layer Observability

How It Works

The contract lives in the service that calls the model, not in the prompt. The prompt can describe the rules; only code can enforce them.

Reference shape (Python)

from dataclasses import dataclass
from typing import Callable, Generic, TypeVar
T = TypeVar("T")

@dataclass
class Ok(Generic[T]):
    value: T
    attempts: int

@dataclass
class Degraded:
    reason: str          # the last violated rule, e.g. "refund_le_order_total"
    attempts: int

Rule = tuple[str, Callable[[T], bool], str]  # (id, predicate, message fed back to model)

def two_gate(call: Callable[[str | None], T], rules: list[Rule], max_repairs: int = 2) -> Ok[T] | Degraded:
    feedback = None
    for attempt in range(1, max_repairs + 2):
        out = call(feedback)                        # gate 1: call() parses against the schema or raises
        failed = next((r for r in rules if not r[1](out)), None)
        if failed is None:
            return Ok(out, attempt)
        metrics.incr("output_contract.violation", tags={"rule": failed[0]})
        feedback = f"Your previous answer violated: {failed[2]}. Fix only that."
    return Degraded(reason=failed[0], attempts=attempt)

rules = [
    ("refund_le_order_total", lambda r: r.refund_amount <= order.total, "refund_amount must be ≤ the order total"),
    ("order_exists",          lambda r: orders.exists(r.order_id),       "order_id must be one of the IDs in the context"),
]

Two details matter more than they look. First, the feedback names one rule. Pasting a full validation trace back into the prompt makes the model rewrite fields that were already correct. Second, Degraded is a distinct type. Callers have to handle it, so "we returned the last attempt anyway" can't be done by accident.

What Fights Back

Format constraints that tax reasoning

Forcing a model straight into a strict schema can reduce answer quality on reasoning-heavy tasks.[3] Mitigation: let the model reason in a free-text field (or a separate call), then extract into the schema. Gate 2 checks the extracted fields, not the reasoning.

Degradation storms after a model update

A new model snapshot that phrases things differently can trip a strict rule on 30% of traffic at once. Mitigation: alert on each rule's violation rate, and roll out rule changes behind a flag, the same way as prompt changes.

The judge becomes the bottleneck

LLM-as-judge validators add a second non-deterministic dependency with its own latency and outages. Mitigation: run them last, only on fields that deterministic rules can't cover, and design them to fail open to Degraded, never to "pass".

The Evidence

  • measuredBetween the March and June 2023 GPT-4 snapshots, directly executable code generations fell from 52.0% to 10.0%, mostly because of added formatting rather than wrong code.[1] Output format is a property that drifts between model versions.
  • measuredOpenAI reported that constrained decoding raised complex-schema adherence from under 40% (gpt-4-0613) to 100% (gpt-4o-2024-08-06 with Structured Outputs).[2] Gate 1 is effectively a solved problem on supported providers.
  • measuredTam et al. found that strict format restrictions such as JSON mode can measurably degrade LLM reasoning performance compared with looser formats.[3]
  • reportedValidation-and-retry libraries such as Instructor became popular by wrapping exactly this loop: a Pydantic model with validators, plus automatic re-asks on validation errors.[4]
  • inferenceOnce shape errors are gone, the remaining error budget is almost entirely semantic. Without gate 2, those errors are absent from every dashboard built on parse rates.

But what if the model is good enough now?

It may well be, for your current prompt, your current traffic and your current snapshot. The contract isn't a bet that the model is bad. It's a sensor for the day one of those three changes. Rules that never fire cost microseconds. Rules that fire tell you about a regression before your users do.

Recall Practice

Why can structured outputs reduce how visible errors are?

Because they remove the parse failures that used to signal confusion. A confused model now produces a well-formed wrong value, which passes every check built only on shape.

What should repair feedback contain?

The single violated rule in plain language. A full error dump invites the model to rewrite correct fields and anchors it to its mistake.

What does the loop return when the repair budget runs out?

A typed degraded result that the caller has to handle, never the last invalid attempt.
