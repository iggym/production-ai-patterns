Your Budget Is a Receipt

Per-workflow cost caps and the budget-enforced proxy pattern for LLM systems.

March 14, 2025

Three Things You Didn't Know You Needed

Cost tracking belongs in the proxy layer, not the application layer.
Model degradation is governance, not failure.
Your pricing data has a half-life of weeks, not months.
Common Belief → Reframe

"Set a monthly budget and alert when you're close."

"Enforce cost per request, before the token is generated."

A budget ceiling is a postmortem tool dressed up as a guardrail.

In February 2025, an engineer posted to HackerNews about opening a $14,000 OpenAI invoice for an internal summarization tool — a tool that had been working correctly for three months. No bugs. No runaway loops. No misconfigured retry logic. Just a workflow that called GPT-4o for every Slack thread in a growing company, with no per-request cost enforcement. The tool did exactly what it was built to do, on more threads than ever, because the company had grown. That was the problem. The engineer's post ended with a line that stuck: "I built the feature right. I just never built the meter."

Receipt, Not Brake

Before

Most engineers think cost governance means setting a monthly spend ceiling and wiring up an alert. The budget tells you when you're close to the limit.

After

A monthly budget tells you what you already spent. It cannot stop a single workflow from burning through your allocation before the alert fires. By the time the alert triggers, the tokens are already generated, the API call is already billed, and the money is already gone.

The Budget-Enforced Proxy

The pattern that actually prevents the 3am page is structurally different. It places cost enforcement inside the request path itself — not as a sidecar metric, not as a monthly reconciliation, but as a gate that every LLM call passes through before a single token is generated.

LiteLLM, an open-source LLM proxy maintained by BerriAI, implements this through "virtual keys." Each key carries an attached budget. When a workflow makes a call through the proxy, LiteLLM checks the remaining budget on that key before routing the request to OpenAI, Anthropic, or any other provider. If the budget is exhausted, the proxy returns a 429 without touching the provider API. The application gets a clean signal it can handle — retry with a cheaper model, queue the work, or surface an error to the user. The provider never sees the request. The money never leaves the account.

The architecture is deliberately simple. Your application code calls a local proxy endpoint instead of calling the LLM provider directly. The proxy holds the budget state, does the math on estimated tokens and current pricing, and either forwards or blocks. No changes to your application logic beyond swapping an endpoint URL and attaching a key.

What Breaks Without It

Two forces work against the obvious solutions. First, cost isn't visible at the point of the LLM call unless something in the request path computes it. Application code typically sends a prompt and receives a completion — the cost is a billing-line item that arrives days later, in a different system, owned by a different team. You cannot govern what you cannot see at the point of decision. Second, the person who builds the workflow rarely controls the billing account. The engineer writing the summarization tool and the engineer who gets paged about the invoice are often different people, in different on-call rotations, looking at different dashboards. The governance gap is also an organizational gap.

Degradation Is the Point

Before

Most teams treat falling back to a cheaper model as a failure mode — something that happens when the primary model is down or latency spikes.

After

In cost governance, degradation is the primary mechanism. When the budget tightens, the gateway silently steps down the model chain. The output quality changes. The spend does not exceed the cap. A governed output that's slightly worse is a working system. An ungraded output is the actual failure.

Portkey, an AI gateway, implements this as "cost-gated routing": a workflow specifies a chain — GPT-4o first, then Claude 3.5 Sonnet, then GPT-4o-mini — and the gateway checks the remaining budget before each call. When the budget tightens, the gateway silently steps down the chain. The output quality changes. The spend does not exceed the cap.

The strongest counterargument to this approach — that degraded output damages user trust — falls apart under inspection: an ungraded output is the actual failure, because it means the system ran out of money and stopped entirely. A governed output that's slightly worse is a working system. The user gets a summary. It's not as good. The system is still running.

The Stale Baseline Trap

There's a third force that catches teams who do everything else right. LLM pricing changes. Between January and March 2025, OpenAI adjusted GPT-4o-mini pricing, Anthropic changed token-counting behavior for Claude models, and several providers modified how they count input versus output tokens. A cost cap calibrated in December can be 30 to 50 percent off by March — not because the workflow changed, but because the unit economics shifted under it. The pattern here is the Stale Cost Baseline: your governance math is only as good as your pricing data, and pricing data decays fast in this market.

The fix is to make the proxy's pricing table a live configuration, not a hardcoded constant. LiteLLM pulls pricing from its own maintained registry. Portkey updates its cost calculations when providers change their rates. If you're building this yourself, the pricing table needs its own update cadence — weekly at minimum, tied to provider changelogs, with its own test that verifies the numbers match what the provider actually bills.

Cost governance and reliability governance are the same pattern applied to different failure axes — which means the team that builds your retry logic should be the team that builds your cost caps, even though org charts rarely put them together.

The Cost Governance Checklist

Before any LLM-backed workflow reaches production, four conditions must hold:

  1. Every call path passes through a proxy that can compute estimated cost before the provider is touched.
  2. Each workflow — not each team, not each project, each workflow — has an independent budget cap.
  3. A degradation ladder exists: if the cap is tight, which cheaper model gets the request instead?
  4. The pricing table backing your cost estimates has an explicit refresh cadence, not a "we'll update it when we notice" policy.

If the answer is "an alert," you don't have cost governance. You have a notification about money you already spent.

Open your LLM provider's billing dashboard right now. Find the single workflow with the highest spend last month. Ask yourself: if that workflow's cost doubled tomorrow, what would stop it? What's the structural difference between a monthly budget and a budget-enforced proxy?

Monthly budget is retrospective — it tells you what you spent after the fact. A proxy is preventive — it blocks the request before the provider is touched and money leaves the account.
