PATTERN-0603 · SECURITY

The Lethal Trifecta Is an Architecture Bug

Prompt injection is not a filtering problem you can tune away; it is a capability-composition problem you have to design away.

September 1, 20267 min readResearch window: 2026-07-21 → 2026-09-01

Three things you didn't know you needed

  1. A 99.9% injection filter fails every day at scale. Read 10,000 untrusted documents a day at a 0.1% bypass rate, and you should expect about ten successful injections a day.
  2. The vulnerability is a property of the context window, not of any one tool. Each tool is safe on its own. The breach happens when three capabilities share one model context.
  3. Rendering is a tool. A markdown image URL that your UI fetches automatically is an outbound channel, even if your agent has no "send" tool.

Zero Clicks, One Email

In June 2025, Aim Security disclosed EchoLeak (CVE-2025-32711), a zero-click vulnerability in Microsoft 365 Copilot.[2] The attacker didn't need the victim to click anything. They sent an ordinary-looking email containing instructions addressed to the AI, not to the human.

Later, when the user asked Copilot an unrelated business question, retrieval pulled that email into context alongside the user's private data. The injected instructions told the model to embed sensitive content into a link the client would fetch, and the data left the tenant. Microsoft fixed it server-side. The architecture that made it possible is still how most agents are built.

That same month, Simon Willison gave the shape a name: the lethal trifecta.[1] Any agent that combines (1) access to private data, (2) exposure to untrusted content and (3) a way to communicate externally can be made to steal that data. Whoever controls the untrusted content can steer the model.

You Can't Filter Your Way Out of Composition

The usual defence is detection: classifiers, delimiter tricks, "ignore any instructions in the following text". These are worth having. They are also probabilistic defences against an adversary who can iterate for free. Researchers showed in 2023 that indirect prompt injection works through any content an LLM application retrieves, including web pages, emails and documents.[3] OWASP ranks prompt injection as the top risk for LLM applications.[4]

The reframe: stop asking whether the model will notice the attack, and start asking whether the attack can succeed even if the model obeys it. If no single model context holds all three capabilities, a fully hijacked model still has nothing to exfiltrate, or nowhere to send it.

Orthodox view

  • Detect and strip malicious instructions.
  • One capable agent with many tools.
  • Security review per tool.
  • Success = filter catch rate.

Production reality

  • Assume some injection will succeed.
  • Contexts partitioned by capability.
  • Security review per context: which legs are present?
  • Success = no context holds all three legs.
PATTERN-0603 · SECURITY

Trifecta Partition

Intent
Guarantee by construction that no model context simultaneously holds private data, untrusted content and an outbound channel.
Context
Assistants and agents that read external content (email, web, tickets, uploaded files, third-party tool output) and also touch user or company data.
Problem
The model can't reliably tell data from instructions. Whoever authors the untrusted content can steer any capability present in the same context.
Forces
  • Capability vs. containment: the most useful agent is the one with every tool, which makes it the most dangerous.
  • Fidelity vs. isolation: passing untrusted content as structured, constrained values loses nuance.
  • Latency vs. separation: extra model calls and orchestration hops.
  • Hidden channels: rendering, link unfurling and logging can all leak data.
Solution
  1. Inventory legs per context: for every model call, record whether it has private data (P), untrusted content (U) and an outbound channel (X). Include rendering and auto-fetch as X.
  2. Split the reader: a quarantined model reads untrusted content with no tools and no private data. It returns constrained values only: enums, numbers, spans validated against a schema.
  3. Privileged planner: a model with P and tools never sees raw untrusted text. It handles references to the quarantined output, which the orchestrator substitutes only at the final, non-model step.
  4. Close X by default: an allowlist for outbound domains, no automatic image or link fetching for model-generated URLs, and human confirmation for any send to a new recipient.
  5. Enforce in the orchestrator: a policy check refuses to assemble a context that contains P + U + X. This is a hard error, not a warning.
Consequences
Benefits: a successful injection is contained to a context that can't do damage; the security argument stops depending on model behaviour. Liabilities: tasks that need nuanced reasoning over untrusted text plus private data get harder or need a human; more orchestration code; some UX loss (no inline image previews from model output).
Related patterns
Context Firewall · Context-Filtered Gateway Decomposition · Intent-Keyed Tool Ledger

How It Works

This builds on the Dual LLM idea (a privileged model plus a quarantined one, communicating through symbolic references)[5] and on research systems such as CaMeL that enforce capabilities on data flowing out of untrusted sources.[6] The production version is mostly plumbing and policy.

Reference shape (Python): the orchestrator's policy check

from enum import Flag, auto

class Leg(Flag):
    NONE = 0
    PRIVATE = auto()    # P: user/company data in context
    UNTRUSTED = auto()  # U: any third-party-authored text in context
    EGRESS = auto()     # X: tools or renderers that can reach outside

LETHAL = Leg.PRIVATE | Leg.UNTRUSTED | Leg.EGRESS

def assemble_context(parts: list["ContextPart"], tools: list["Tool"], renderer: "Renderer") -> "Context":
    legs = Leg.NONE
    for p in parts:
        legs |= p.legs                          # each retriever tags what it returns
    for t in tools:
        legs |= t.legs
    if renderer.auto_fetches_urls:              # markdown images, link unfurls
        legs |= Leg.EGRESS
    if legs & LETHAL == LETHAL:
        audit.log("trifecta_blocked", parts=[p.source for p in parts], tools=[t.name for t in tools])
        raise TrifectaViolation(legs)
    return Context(parts, tools, renderer)

The hard part is honest tagging. Tool output from a third-party API is UNTRUSTED. A shared document that a colleague can edit is UNTRUSTED. Your own database, if users can write free text into it, is UNTRUSTED too.

Model assumptions: each malicious document independently bypasses the filter with the selected probability, and a bypass in a full-trifecta context results in exfiltration. With any leg removed, this exfiltration path is structurally closed (other risks such as wrong actions or misinformation remain). Illustrative: attackers adapt, so real bypass rates aren't stable.

What Fights Back

The planner still needs to "understand" the email

Summaries from the quarantined reader are free text, and free text can carry instructions. Mitigation: return constrained types (enums, dates, amounts, IDs that match a regex). Where prose is unavoidable, show it to the human, not to the privileged model.

Hidden egress

Image rendering, link previews, analytics beacons, error reports that include context, and even "search the web" tools are all X. Mitigation: treat the client renderer as part of the agent; enforce a strict CSP and turn off auto-fetch for model-authored URLs.

Capability loss users will notice

"Read this thread and reply to everyone with our pricing sheet" is the trifecta by definition. Mitigation: route it through human confirmation that shows the exact recipients and attachments. The human is the policy exception, by design.

The Evidence

  • reportedEchoLeak (CVE-2025-32711) showed a zero-click data exfiltration chain against a major enterprise assistant, triggered by a single inbound email.[2]
  • measuredGreshake et al. demonstrated indirect prompt injection against real LLM-integrated applications, including data theft and remote control through retrieved content.[3]
  • reportedOWASP's 2025 Top 10 for LLM Applications lists prompt injection (LLM01) first and recommends least privilege and segregating untrusted content.[4]
  • measuredThe CaMeL research system showed that enforcing data-flow capabilities around untrusted values can block prompt injection by design, at some cost in task completion.[6]
  • inferenceAny defence with a non-zero bypass rate will eventually fail at volume (see the playground). Removing a leg is the only control whose failure rate doesn't grow with traffic.

But what if the models get robust to injection?

Then the partition costs you some orchestration code and buys you defence in depth. The asymmetry favours partitioning. If you're wrong about model robustness, the partition is what stops the breach. If you're right, it cost little.

Recall Practice

What are the three legs of the lethal trifecta?

Access to private data, exposure to untrusted content, and an ability to communicate externally, all present in one model context.

Why does a 99.9% filter not solve prompt injection?

Because failures scale with volume and attackers iterate. At thousands of malicious inputs, a 0.1% bypass rate means near-certain compromise over time.

Why must the quarantined reader return typed values rather than summaries?

Free-text summaries can carry the injected instructions into the privileged context. Constrained types cannot.
