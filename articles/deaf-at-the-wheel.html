Your RAG system serves 50,000 queries a day. Dashboards glow green — p99 retrieval latency 180ms, LLM call latency 1.2s, error rate 0.3%. Everything within SLA. Then customer complaints spike 40x in a single week. The vector database had silently fragmented its HNSW index after a bulk document update. Retrieval still returned five results in 180ms — but they were the wrong five. Every standard metric said healthy. Every outcome was broken [3].

This isn't a rare edge case. It's the default failure mode of AI in production.

The Wrong Depth

Here's the correction: model health ≠ outcome health. You built your dashboards at the call layer. AI systems fail at the decision layer.

Datadog saw this gap clearly enough to build an entirely separate product. Their existing APM traced HTTP calls to model APIs with sub-millisecond precision — request duration, status code, payload size. But when GPT-4 returned a confidently hallucinated function call, or a RAG pipeline served irrelevant context that the model faithfully summarized into a plausible wrong answer, APM saw 200 OK. Datadog LLM Observability, launched to address precisely this, traces the full semantic chain — prompt construction → model call → output parsing → downstream consumption — annotating each span with quality signals that traditional APM cannot compute [1].

The insight isn't that APM is broken. It's that APM instruments the transport, and AI's critical failures are semantic.

Decision-Layer Observability

Problem. Standard observability instruments the transport — HTTP status, latency, token throughput. AI systems produce failures invisible to these instruments: semantic degradation, retrieval drift, hallucination, format violation. These failures return 200 OK.

Forces. Four forces make naïve solutions fail:

  • Probabilistic outputs. No compiler catches a wrong answer. Every response is potentially valid syntax and catastrophically wrong semantics.
  • Continuous drift. Quality degrades between deployments — embedding models go stale, knowledge bases diverge, user intent shifts. Batch evaluation at deploy time misses everything after.
  • Evaluation cost. Running a judge LLM on every output can double your inference bill. The naïve fix is economically infeasible at scale.
  • Tooling mismatch. APM and metric systems assume deterministic software. They have primitives for counts and durations, not for "relevance" or "faithfulness."

Solution. Three moves, in order:

  1. Pipe evaluation scores into observability as first-class metrics. Relevance, faithfulness, correctness — these are your p99 equivalents. Arize Phoenix was built for exactly this: it runs evaluation on production traces and writes scores back as span attributes, not as a separate batch report. Evaluation becomes a runtime signal, not a CI artifact [2].
  2. Sample, don't scan. Stratified sampling of 5–10% of production traffic gives you 95% confidence intervals on quality metrics at a fraction of the cost. You need a representative slice continuously — not every request.
  3. Alert on decision-quality distributions, not call-level thresholds. A drop in mean relevance score from 0.87 to 0.72 over four hours is your production incident — not a latency spike.

Consequences. You gain detection of semantic drift within minutes instead of days. You pay 10–30% additional compute for evaluation inference. You must operate evaluation infrastructure (judge models, scoring pipelines, eval datasets) as a production system, not a notebook. And you may discover your quality was worse than you thought — the green dashboards were masking real problems all along.

Where the Seams Split

Consider a production RAG stack: documents enter through LlamaIndex's SentenceSplitter, get embedded with OpenAI's text-embedding-3-small, and land in Pinecone Serverless on a p2 index. At query time, the same embedding model vectorizes the question, Pinecone returns five nearest neighbors, Cohere's rerank-english-v3.0 re-scores them, GPT-4o synthesizes an answer, and LangSmith logs the trace — latency, token count, tool calls. All green [3].

The observable seam sits between retrieval and generation. Pinecone reports search latency and result count. It does not report whether those five results are relevant to the query. As the index fragments or the embedding model drifts from the corpus, retrieval degrades semantically while remaining healthy operationally. The LLM faithfully summarizes irrelevant context into a confident wrong answer. LangSmith records a successful trace. The user gets garbage.

Decision-Layer Observability inserts instrumentation at the seam: a relevance evaluator scores the retrieved context against the query before generation proceeds. That score — not retrieval latency — is the metric that catches the failure.

The observability gap in AI systems is isomorphic to the test gap: if you can't evaluate it continuously, you can't observe it continuously.

Credibility and Nuance

Datadog built a separate LLM Observability product because APM couldn't detect semantic failure [1]. Arize Phoenix pipes evaluation into traces because batch evaluation detects drift days late [2]. The RAG retrieval-relevance gap is documented across vector database operator postmortems in Q1 2025 [3].

Counterargument: evaluation is too expensive to run on production traffic. You don't need every request. Stratified sampling at 5–10% gives you 95% confidence intervals at ~10% of the evaluation cost — and you already pay far more for the undetected failures your green dashboards are hiding.

This Week's Moves

  1. List decisions, not calls. Enumerate every AI-powered decision your system makes — every point where model output drives a user-visible action or downstream behavior.
  2. Identify the outcome signal. For each decision, name the observable signal that tells you the outcome was good. If none exists, you need a judge or a feedback loop.
  3. Instrument at the seam. Add evaluation-score metrics at the boundary between retrieval and generation, and between generation and consumption.
  4. Alert on distributions. Set alerts on quality-score means and percentiles, not on latency or error rate alone. A slow drift from 0.9 to 0.7 over a day is an incident.
  5. Chaos-test your dashboards. Deliberately degrade retrieval quality and verify your instrumentation detects it within 10 minutes.
