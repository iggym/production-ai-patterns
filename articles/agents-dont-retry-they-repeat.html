PATTERN-0602 · RELIABILITY

Agents Don't Retry, They Repeat

An agent that re-issues a timed-out tool call is not retrying — it is acting twice, and your retry policy never saw it happen.

August 25, 20268 min readResearch window: 2026-07-14 → 2026-08-25

Three things you didn't know you needed

  1. Your agent has a retry policy you never configured. When a tool returns a timeout error, the model reads it and often calls the tool again. No backoff, no jitter, no idempotency key, and none of it shows up in your HTTP client config.
  2. Key on intent, not on arguments. On a second attempt a model regenerates the arguments with cosmetic differences: a reworded memo, a reordered list. A hash of the raw arguments treats them as a new request.
  3. A timeout is not a failure. It is an unknown. The side effect may have committed. You have to find out before you act again.

The Refund That Happened Twice

Illustrative scenario, a composite of a common failure shape. A support agent is asked to refund a damaged order. It calls issue_refund(order_id, amount=84.00, memo="Damaged on arrival"). The payment provider commits the refund, then the response takes longer than the tool's 30-second timeout. The agent framework passes the timeout error back to the model.

The model does what a helpful assistant does. It apologises for the delay and tries again, this time with memo="Refund: item damaged on arrival". The second call succeeds. The customer receives two refunds. The HTTP client's retry policy (three attempts, exponential backoff, idempotent methods only) never fired, because from its point of view these were two separate, successful POSTs.

Now replace "refund" with "provision a VM", "send an email to 4,000 customers" or "drop a table". In July 2025, a widely publicised incident saw an AI coding agent on Replit delete a production database during an explicit code freeze. The company's CEO publicly apologised and announced stronger separation between development and production.[5] Duplication and destruction are the same root problem: the model decides when side effects happen, and nothing in the tool layer makes that decision safe to repeat.

Idempotency Moves From the API to the Agent

Distributed-systems engineers solved this years ago. Stripe made idempotency keys a first-class part of its API so a client can retry a charge without double-charging.[1] AWS builds the same idea into its APIs as client request tokens: the same token returns the same result, and the same token with different parameters is rejected.[2]

Those designs assume the client is deterministic code that generates one key per logical operation and reuses it. An LLM agent breaks that assumption. It doesn't know which of its calls are logically the same, and it regenerates arguments freely. The idempotency key has to come from somewhere the model can't paraphrase.

Orthodox view

  • Retries are configured in the HTTP client.
  • Tools are thin wrappers around APIs.
  • Timeout → error → let the model decide.
  • Destructive tools are guarded by the prompt.

Production reality

  • The model is the outermost retry loop.
  • Tools sit behind a ledger that records intent and outcome.
  • Timeout → unknown → reconcile before re-executing.
  • Destructive tools need a commit token the model can't make up.
PATTERN-0602 · RELIABILITY

Intent-Keyed Tool Ledger

Intent
Make every side-effecting tool call safe to repeat by recording its intent before execution and its outcome after, keyed on fields the model can't cosmetically change.
Context
Agents with write tools (payments, provisioning, messaging, data mutation) running on a network that can time out.
Problem
Model-driven re-invocation bypasses transport-level retry safety. Paraphrased arguments defeat naive deduplication, and timeouts hide whether the side effect committed.
Forces
  • Safety vs. autonomy: blocking repeats can block legitimate repeated intent (two separate $20 refunds).
  • Latency vs. certainty: reconciling an unknown outcome costs a read before every retry.
  • Coverage vs. effort: not every downstream API accepts idempotency keys or offers a status query.
Solution
  1. Classify every tool as read-only, idempotent, compensable or irreversible. Store this in code, not just in tool descriptions.
  2. Declare intent fields per tool (for issue_refund: order_id, amount_cents). Derive the key as hash(run_id, tool, canonical(intent_fields)).
  3. Write-ahead: insert PENDING into the ledger before executing, and pass the key downstream as the idempotency key wherever the API supports one.
  4. On timeout, mark UNKNOWN and reconcile against the downstream system before allowing another execution.
  5. On repeat, replay: return the recorded outcome to the model ("already completed at 14:02, refund re_123"), so it sees the result and doesn't try a third time.
  6. Irreversible tools take two steps: plan_* returns a dry-run diff and a single-use commit token; commit_* requires that token, issued outside the model's control.
Consequences
Benefits: duplicate side effects become structurally impossible for keyed tools; replayed results stop the model's retry spiral; the ledger becomes an audit log. Liabilities: a new stateful dependency on the hot path; intent-field design takes judgement for each tool; legitimate repeats need an explicit nonce.
Related patterns
Bounded Cascade Degradation · Spend-State Circuit Breaker · Two-Gate Output Contract

How It Works

Reference shape (TypeScript)

type Status = "PENDING" | "COMMITTED" | "FAILED" | "UNKNOWN";
interface ToolSpec<A> {
  name: string;
  kind: "read" | "idempotent" | "compensable" | "irreversible";
  intentFields: (keyof A)[];                         // what makes two calls "the same act"
  execute(args: A, key: string): Promise<unknown>;   // pass key downstream
  reconcile?(key: string): Promise<unknown | null>;  // query outcome by key
}

async function invoke<A>(spec: ToolSpec<A>, runId: string, args: A) {
  if (spec.kind === "read") return spec.execute(args, "");
  const key = sha256([runId, spec.name, canonical(pick(args, spec.intentFields))].join("|"));
  const prior = await ledger.get(key);
  if (prior?.status === "COMMITTED") return { replayed: true, result: prior.result };
  if (prior?.status === "UNKNOWN" || prior?.status === "PENDING") {
    const found = await spec.reconcile?.(key);
    if (found) { await ledger.set(key, "COMMITTED", found); return { replayed: true, result: found }; }
    if (!spec.reconcile) return { blocked: true, reason: "outcome unknown; needs human check" };
  }
  await ledger.set(key, "PENDING");
  try {
    const result = await spec.execute(args, key);
    await ledger.set(key, "COMMITTED", result);
    return { replayed: false, result };
  } catch (e) {
    await ledger.set(key, isTimeout(e) ? "UNKNOWN" : "FAILED");
    throw e;
  }
}

Note what memo doesn't do: it isn't an intent field, so the paraphrased second call hashes to the same key. When a user really wants two identical refunds, the conversation layer adds an explicit nonce (for example, the user turn ID) to the intent fields.

Model assumptions: each attempt times out independently with the selected rate. A timed-out attempt committed its side effect with the selected probability. The model keeps re-attempting until success or the cap. Without a ledger, every committed attempt after the first is a duplicate. With a ledger, keyed tools never duplicate, and each timeout costs one reconciliation read.

What Fights Back

The ledger is now on the critical path

If the ledger is down, every write tool is down. Mitigation: keep it in the same datastore as the agent's run state (so it fails together with the run, not separately), and fail closed for irreversible tools and open, with an alert, for compensable ones.

Intent fields that are too coarse or too fine

Too coarse (just order_id) blocks a legitimate second partial refund. Too fine (including memo) lets paraphrases through. Mitigation: review intent fields like a database unique constraint, and test them with paraphrased calls generated by the model itself.

Downstreams that can't reconcile

Some APIs have no idempotency key and no status query. Mitigation: mark those tools UNKNOWN → blocked and route to a human. A stuck run is cheaper than a second wire transfer.

Tool annotations are hints, not controls

The Model Context Protocol lets servers mark tools idempotentHint or destructiveHint,[4] but the spec treats these as untrusted hints. Your gateway still has to enforce the classification itself.

The Evidence

  • reportedStripe's API uses client-supplied idempotency keys so that a retried request returns the original result instead of executing again. Keys can be pruned after at least 24 hours.[1]
  • reportedThe AWS Builders' Library describes client request tokens that return the same response for repeated requests and reject reuse with different parameters. The same "same intent, same key" contract applies here.[2]
  • reportedRetries amplify load and failures unless they're bounded and coordinated across layers.[3] An agent loop adds a layer that most retry budgets don't account for.
  • reportedThe July 2025 Replit incident showed an agent taking a destructive production action despite instructions not to.[5] Prompt-level guards aren't execution-level guards.
  • inferenceBecause models paraphrase on regeneration, hashing raw arguments gives a false sense of deduplication. Only declared intent fields are stable.

But what if the framework already retries tool calls?

Then you have two retry loops, the framework's and the model's, and neither knows about the other. The ledger doesn't replace either one. It makes both safe by turning their repeats into replays.

Recall Practice

Why doesn't the HTTP client's retry policy prevent duplicate agent actions?

Because the model issues a new, independent request after reading the timeout error. From the transport's point of view, both calls are fresh and successful.

Why hash intent fields instead of the full arguments?

Models paraphrase free-text arguments when they regenerate a call, so a full-argument hash treats the same act as a new one.

What happens when a keyed call is repeated after it committed?

The gateway returns the recorded outcome to the model as a replay, which also stops the model from trying again.
