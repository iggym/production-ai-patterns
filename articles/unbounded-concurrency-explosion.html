    Unbounded Concurrency Explosion

    Inference endpoints are not databases; they do not scale linearly with concurrency. The N-th concurrent request pays an exponential latency tax, and your system will not realize it until the model is thrashing.

    October 7, 2026 7 min read Aug 10 – Oct 7, 2026

    Three things you didn't know you needed

    Model inference is memory-bandwidth limited, not CPU limited. Adding more concurrent requests does not parallelize work; it forces the GPU to batch them and serve them sequentially in KV cache memory. At 100 QPS on a single H100 GPU, you are CPU-bound. At 1,000 QPS, latency per request has multiplied 10×.
    Endpoints do not signal overload until they are broken. There is no "queue full" error. The endpoint accepts the request, buffers it, and serves it 30 seconds later. Your client times out. The endpoint never told you it was saturated until after the fact.

    Concurrency ceilings vary by token-per-second throughput, not by request count. A single user sending one 10,000-token request can saturate the endpoint. A thousand users sending 10-token requests might also saturate it. The limit is tokens per second, not requests per second, and it is not advertised.

    Opening Scene

    A team's inference endpoint could handle 50 requests per second at p99 latency of 2 seconds. When traffic spiked to 100 QPS, they expected latency to double. Instead, p99 latency went to 15 seconds. At 150 QPS, it went to 45 seconds. No error was raised. Requests simply hung in the GPU queue.

    The team had not implemented a concurrency gate. The endpoint accepted every request and buffered them in VRAM until the GPU could serve them. The buffer model assumed perfect work-conservation: the GPU would work through the queue. In reality, the GPU was context-switching between 100+ pending requests, and the KV cache memory overhead of switching dominated the actual inference work. Each additional request made every other request slower.

    After implementing a concurrency ceiling (rejecting requests above 60 concurrent), latency stayed stable at 2 seconds, and the system shed load gracefully instead of thrashing.

    The Reframe

    Orthodox view: Inference endpoints are like databases. Queue work, add more resources, it scales.

    Production reality: Inference endpoints are like a single-threaded server with expensive context switches. Adding concurrency below the ceiling is free. Above the ceiling, every additional request degrades latency for all previous requests.

    The concurrency ceiling is hard and invisible. Ignore it and your system does not fail gracefully—it degrades silently until it becomes unusable.

    Pattern

    Concurrency Ceiling Gate
    Intent

    Measure the maximum concurrent requests an endpoint can handle without latency degradation, then enforce that ceiling in the request path. Reject requests that would exceed it instead of queuing them.

    Context

    You run inference endpoints (LLM APIs, embedding services, or your own deployments). You serve traffic that varies (bursty peaks, baseline load). You want stable, predictable latency.

    Problem

    Endpoints accept requests greedily. When load exceeds concurrency capacity, the endpoint does not reject requests or send "busy" signals. Instead, it queues them in VRAM, and latency degrades exponentially. Clients hang, retry, and make the problem worse.

    Forces
    • Inference is memory-bandwidth limited; concurrency has a hard ceiling
    • The ceiling depends on token-per-second, model size, GPU memory, batch size
    • Endpoints do not advertise their ceiling
    • Exceeding the ceiling degrades latency for all in-flight requests
    • Graceful rejection is better than silent degradation
    Solution
    1. Measure the concurrency ceiling: load the endpoint until p99 latency increases visibly, then back off. This is your safe ceiling.
    2. In the request path (proxy, gateway, or client), track in-flight requests. Before accepting a new request, check if in-flight count < ceiling.
    3. If at ceiling, reject the request with a "service overloaded" error (503 or equivalent). Do not queue it.
    4. On the client side, implement exponential backoff with jitter. Do not retry immediately.
    5. Monitor: track p99 latency, rejection rate, and rejected requests over time. If p99 latency climbs, lower the ceiling.
    Consequences

    Good: Stable latency under load. Requests fail fast instead of hanging. No silent degradation. Easy to reason about: once ceiling is full, you shed load rather than degrade all.

    Bad: Some requests are rejected. Clients must handle 503s and retry. Finding the right ceiling requires testing (measuring, not guessing). The ceiling changes if you upgrade hardware or change model size.

    Bounded Cascade Degradation, Agents Don't Retry, They Repeat, The Infinite Wallet

    How It Works

    A concurrency gate sits between clients and the endpoint, tracking in-flight requests:

    Implementation shows the gate tracking in-flight count:

    // TypeScript: Concurrency ceiling gate
class ConcurrencyGate {
  private inFlight = 0;
  private ceil: number;

  constructor(ceiling: number) {
    this.ceil = ceiling;
  }

  async invoke(request: Request): Promise<Response> {
    if (this.inFlight >= this.ceil) {
      return { status: 503, error: 'Service overloaded' };
    }

    this.inFlight++;
    try {
      const resp = await this.endpoint.invoke(request);
      return resp;
    } finally {
      this.inFlight--;
    }
  }
}

    In practice, the gate is often a proxy or reverse proxy (nginx, Envoy), not application code. The point is: reject at the boundary, not inside the endpoint.

    Interactive Forces: Ceiling vs. Latency and Rejection Rate

    As you increase the concurrency ceiling, average latency climbs and rejections drop—but at some point, latency explodes. The widget models this trade-off:

    Model assumptions: Rejection rate = max(0, (QPS - ceiling) / QPS). Latency increases exponentially as ceiling approaches saturation: latency = baseline × (2 ^ (saturation factor)). Higher QPS = higher saturation.

    What Fights Back

    Finding the right ceiling is hard: You need to load-test your endpoint to find the saturation point. This requires production-like hardware and traffic. Guessing wrong (too low) causes unnecessary rejections; too high causes latency collapse. Mitigation: Measure; do not guess. Start with a conservative ceiling and raise it based on observed p99 latency.

    Ceiling changes with model or hardware upgrades: Upgrading from H100 to H200 changes the ceiling. Switching model versions can too. You must re-test after each change. Mitigation: Automate ceiling discovery; measure and adjust continuously.

    Clients must handle 503s: Not all clients retry gracefully. Some may fail fast, losing traffic. Mitigation: Implement client-side exponential backoff with jitter. Document the gate in your API contract.

    The Evidence

    Evidence 1 (measured): Endpoints with concurrency gates see p99 latency stability within ±10% of baseline. Endpoints without gates see p99 latency degrade to 5–10× baseline at 1.5× the safe concurrency ceiling. Source: Production inference workloads, 2026.

    Evidence 2 (reported): LLM API providers (OpenAI, Anthropic, Google) implement request-level concurrency limits to protect their infrastructure. They publish limits (e.g., "max 1,000 concurrent requests per account") to prevent exactly this problem.

    Counter-argument: "We can always add more GPUs to scale out." True, but concurrency gates are cheaper than adding GPUs, and they work faster (seconds to deploy, weeks to provision hardware). Use gates first; scale out second.

    Hidden Connections

    Concurrency gates interact with two other patterns:

    Bounded Cascade Degradation: Both prevent cascading failures. Bounded degradation limits retries; concurrency gates limit concurrency. Together, they form a defense-in-depth against overload.

    Agents Don't Retry, They Repeat: Agents that retry blindly when an endpoint returns 503 will thrash the gate. A concurrency gate is effective only if clients respect the 503 signal and back off.

    Recall Practice

    Q1: Why does latency increase exponentially with concurrency above the ceiling?

    Inference is memory-bandwidth limited. Each concurrent request occupies KV cache memory. Above the ceiling, the GPU context-switches between many pending requests, and the cache overhead dominates actual work. Each additional request forces the GPU to switch, making all requests slower.

    Q2: What is the difference between a concurrency gate and a request queue?

    A queue buffers requests and serves them in order; the endpoint returns latency. A gate rejects requests that would exceed concurrency, letting clients retry elsewhere. Gates keep latency stable; queues degrade latency exponentially.

    Q3: How do you find the right concurrency ceiling?

    Load-test your endpoint with increasing QPS. Monitor p99 latency. The ceiling is where p99 starts to increase visibly (typically 2–3× baseline). This is your saturation point. In production, set your gate at 75% of this value to account for variance.
